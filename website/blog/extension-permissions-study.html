What permissions do new tab and focus extensions really ask for?

By Adnan · October 23, 2026 · 13 min read

Every browser extension has to declare what it can do. That declaration, a file called manifest.json, is public for open-source projects, so anyone can read it. We read it for seven popular open-source new tab, focus and blocking extensions and put the results in one place: what each one asks for, which asks are optional, and what the pattern says about how to judge an extension.

Disclosure: I make WebWell, and it is one of the seven. It is also the extension that asks for the most required permissions, and I haven't hidden that. The data is from public files that anyone can download, the method is below, and a CSV of the full dataset is free to use.

Why this is worth checking

An extension runs inside the program you use for almost everything: email, banking, work. A new tab page looks harmless, but depending on what it asks for, an extension can see which sites you visit, read what is on a page, or change it. Most people accept the install prompt without reading it, and the store listing seldom explains why each permission is there.

The question is not "is this extension safe?", which a permission list cannot answer. It is smaller and easier: does what it asks for match what it does? A clock does not need to read every page. A site blocker has a real reason to see which address you are visiting. This study maps those asks so you can make the comparison yourself.

How we did it (and how to repeat it)

We picked seven open-source extensions in four categories that people use to feel calmer or more focused: new tab pages, a Pomodoro timer, site and feed blockers, and a time tracker. We used open-source projects on purpose, because their manifests are public on GitHub and anyone can check our numbers. For each one we downloaded the manifest from the project's default branch on 2026-10-22 and recorded:

  • the required permissions (granted when you install),
  • the optional permissions (requested later, when you use a feature),
  • whether it asks for access to all websites, and whether that is required or optional,
  • whether it replaces the new tab page, plus its licence, version and the date of its last code change.

We read the Chromium (Chrome and Brave) version where a project ships separate manifests. To repeat the check, download each file yourself:

# LeechBlock NG

Because default branches move on, files you download later may differ from our snapshot, which is why every figure here carries a date.

What the numbers show

1. The two plain new tab pages ask for almost nothing

Tabliss requires only storage, and Bonjourr requires only storage too, with three optional extras (bookmarks, topSites and search) that it asks for when you use the matching feature. Both replace your new tab page and neither requests access to any website. If all you want is a calm page with a clock and a photo, this is the baseline, and anything that asks for much more should be able to say why.

2. Permissions follow features

Once an extension needs to know where you are in the browser, the ask grows. LeechBlock NG, ActivityWatch Web Watcher, WebWell request tabs and/or webNavigation, because tracking time or blocking a site starts with knowing the address of the page. Those are exactly the permissions that Chrome words as reading your browsing history. That is not suspicious by itself: it is what the feature costs. It is a reason to check what the extension says it does with that information.

3. All-sites access is the real dividing line

Access to every website is the broadest permission on the list: Chrome describes it as being able to read and change your data on all websites. The seven split three ways:

  • Required at install (2): LeechBlock NG, ActivityWatch Web Watcher. For a site blocker or a tracker that watches every tab, this follows from the job, but it also means you grant it before you have used a feature.
  • Optional (2): News Feed Eradicator, WebWell. The extension asks only when you switch on a feature that needs it, and works without it until then.
  • Never requested (3): Tabliss, Bonjourr, Marinara.

The optional model is better for you as a user, because the permission arrives with a reason and you can say no. It costs the developer some convenience, which is probably why it is not the norm.

4. A permission count is a poor safety score

It is tempting to rank extensions by how many permissions they list. The data argues against it. WebWell lists the most required permissions (11) but keeps all-sites access optional. LeechBlock NG lists 6 and requires access to every website. Most of what WebWell asks for is individually narrow: alarms, idle and offscreen, for example, have no install warning of their own. What matters is what a permission lets the extension see or change, not how many there are.

Since WebWell is mine, here is why it lists eleven. It is a new tab page, a focus timer, a site and short-video blocker, a time tracker and a music player in one extension, and each feature needs its own few permissions. The privacy policy explains each one, and all the code is public, so you can check the claim instead of trusting it. If you only want a new tab page, Tabliss or Bonjourr will ask you for far less, and that is a fair reason to choose either.

5. Maintenance matters as much as permissions

An extension with a tiny permission list is still a risk if nobody maintains it. 5 of the 7 repositories saw code changes in the 90 days before our snapshot. Marinara's repository still ships a Manifest V2 manifest and has not changed since 2023-05-28, so what is in the store may differ from what is on GitHub. Tabliss uses Manifest V3 but has had no code pushed since 2024-08-19. Neither fact says an extension is unsafe, but both belong in a decision, and the store page's "last updated" date is worth a look.

6. Open source is what made this possible

All seven are open source, and licences range from MIT to AGPL. That is why anyone can repeat this work. Closed-source extensions can also be inspected once installed, but they are harder to compare side by side, and a public manifest on GitHub does not prove that the store build matches it. Open source narrows that gap: you can read the code, build it yourself, and check for differences.

How to audit any extension in five minutes

  1. Read the install prompt. Chrome lists what the extension can do before you click Add. Treat "read and change all your data on all websites" as a question, not a formality.
  2. Look at site access after install. Open chrome://extensions (or brave://extensions), choose Details, and check Site access. You can change it to "on click" or "on specific sites" for many extensions.
  3. Read the manifest. Turn on Developer mode, note the extension's ID, and open manifest.json from your profile's Extensions folder. On Windows, Chrome keeps it under %LocalAppData%\Google\Chrome\User Data\Default\Extensions\<id>\<version>\ and Brave under %LocalAppData%\BraveSoftware\Brave-Browser\User Data\Default\Extensions\. Look at permissions, optional_permissions and host_permissions.
  4. Match each ask to a feature you use. If you cannot find the feature that needs a permission, ask the developer, or pick another extension.
  5. Read the privacy policy for specifics. Good ones say what is stored, where, and when anything is sent. "We take privacy seriously" says nothing.
  6. Check the date and the source. When was it last updated? Is the code public? Is the developer reachable?

Limits, and how to correct us

  • Seven is a small sample. It is not a representative cross-section of all extensions. The most popular extensions in the store are mostly closed source, and we have not included them.
  • A manifest shows capability, not behaviour. It says what an extension can do. It does not prove what it does. Reading the code, or the privacy policy, is the next step.
  • Repository manifests may differ from store builds. Packaging tools can change or add keys, and the store version may be older or newer than the default branch.
  • A count treats all permissions as equal. storage and history do not carry the same weight, which is why we separate required from optional and highlight all-sites access instead of ranking by count.
  • Snapshots go stale. Stars, versions and permissions all change. Every figure here is dated 2026-10-22.

If we got something wrong about your extension, or you would like it added to the dataset, email info.adnanak@gmail.com or open an issue on GitHub. We will correct the article and note the date of the change here.

Questions

Is an extension with more permissions less safe?

Not necessarily. What matters is what the permissions allow and whether the extension needs them. A long list of narrow permissions can be less risky than one broad one such as access to all websites.

What is the safest kind of new tab extension?

One that asks for the least and does only what you need. In our data, the two plain new tab pages needed only storage to install. If you want a timer, blocking or tracking as well, more permissions are expected, so prefer extensions that ask for broad access only when you turn a feature on.

Why do blockers need access to all websites?

To block or change a page, the browser has to let the extension act on it. Some extensions use the browser's own rule system, which does not read page content. Others run code inside pages. Both can ask for broad access, which is why the reasoning matters more than the permission name.
